01

The cost of a single stall

In order means one slow instruction holds up everyone behind it.

Part 1 · The cost of a single stall

Stuck behind a slow load

lw   x1, 0(x2)      # memory is slow: 12 cycles, or even 200
add  x3, x1, x4     # needs x1 — truly has to wait
sub  x6, x7, x8     # independent! could run now
or   x9, x10, x11   # independent! also stuck
mul  x12, x13, x14  # independent! also stuck
  • An in-order pipeline has one iron rule: instruction i + 1 may not overtake instruction i.
  • So sub, or and mul sit idle behind add, although their inputs are ready and their hardware is free.
Analogy

A supermarket queue where the first customer's card is declined. Everyone behind waits — even the person holding only a bottle of water and exact change.

Part 1 · The cost of a single stall

The fix: let ready work go first

Out-of-order execution keeps a pool of decoded instructions and, each cycle, starts any whose inputs are ready and whose hardware is free — whatever their order in the program.

Slow load waitsIndependent SUB runsIndependent OR runsResults retire in order
Part 1 · The cost of a single stall

The instruction window

  • The pool of decoded instructions the core can choose from is the instruction window — tens to hundreds of instructions in modern cores.
  • The bigger the window, the more independent work the core can find while something slow is pending. That ability to keep busy during a long wait is called latency tolerance.
  • But a bigger window costs chip area and power. Every entry must be watched every cycle.
The goal

Find independent work, and overlap slow operations with useful computation instead of stalling.

02

Which reorderings are legal?

Before running anything early, the core must know what it may not reorder.

Part 2 · Which reorderings are legal?

True and false dependences

TypePatternKind
RAWwrite x1 … read x1a true dependence: data really flows from one instruction to the next. Nothing can remove it.
WARread x1 … write x1a false dependence: no data flows. The two instructions merely reuse the same register name.
WAWwrite x1 … write x1

False dependences exist only because the ISA has a small number of register names — 32 in RISC-V — and compilers reuse them.

Part 2 · Which reorderings are legal?

An example: x1 reused as scratch

(i1) ADD  x1, x2, x3     # writes x1
(i2) SUB  x4, x1, x5     # reads x1         → RAW with i1 (true)
(i3) MUL  x1, x6, x7     # writes x1 again  → WAW with i1, WAR with i2 (false!)
(i4) DIV  x8, x1, x9     # reads the new x1 → RAW with i3 (true)
  • i3's result has nothing to do with i1's. Only the shared name "x1" stops i3 from running early.
  • If i3 ran first, it would overwrite the x1 that i2 still needs (WAR) and could be overwritten by i1 later (WAW).
  • Give i3's result a different home, and both problems disappear.
03

Register renaming

More hidden registers than the program can name — and a table that keeps track.

Part 3 · Register renaming

Many more homes than names

  • The ISA offers 32 architectural register names. Inside, the core has a much larger physical register file — often 128 to 300 entries.
  • A rename table (RAT) records which physical register currently holds each architectural one.
  • Every instruction that writes a register is handed a fresh physical register from a free list. Readers look up the table to find where their input lives.

This is register renaming. Since every write lands in a brand-new register, two writes never collide: WAR and WAW vanish. Only RAW — real data flow — remains.

Analogy

A cloakroom. Your coat isn't stored "on hook 3 because you're guest 3": you get a fresh ticket number each time. Two guests called Sam never mix up their coats.

Part 3 · Register renaming

Try it: rename the four instructions

Register-renaming exercise

Give each destination a fresh physical register. Consumers track the physical version they need; this removes WAR and WAW name conflicts while preserving true RAW dataflow.

Part 3 · Register renaming

When does a physical register come back?

  • When an instruction that wrote x1 is finally confirmed, the previous home of x1 can no longer be needed by anyone.
  • That old physical register goes back on the free list.
  • As long as instructions are confirmed in order, the core never runs out of homes for long. (How "confirmed in order" works comes shortly: the reorder buffer.)
04

Dynamic scheduling

The hardware that watches which instructions are ready and sends them off.

Part 4 · Dynamic scheduling

1964: the scoreboard

The CDC 6600 had a central bookkeeper, the scoreboard, tracking every functional unit and register.

Instructions could execute out of order — a first in history.

But it did no renaming: on a WAR or WAW it simply stalled, and results were not forwarded between instructions.

Its four steps

  1. Issue
  2. Read operands
  3. Execute
  4. Write result
Part 4 · Dynamic scheduling

1967: Tomasulo's algorithm

Robert Tomasulo's design for the IBM 360/91 is the ancestor of nearly every out-of-order core today. Three ideas:

Reservation stations

Waiting areas in front of each functional unit. An instruction waits there, holding the operands it already has.

Tags, not names

A missing operand is labelled with the tag of the station that will produce it — which renames registers automatically.

Common data bus

A finished unit broadcasts (tag, value). Everyone waiting on that tag grabs the value at once.

Analogy

A deli counter. You don't wait for "the person before you" — you wait for your ticket number to be called. When it is, anyone holding that number steps up.

Part 4 · Dynamic scheduling

Worked example: a Tomasulo timeline

i1: MUL x1, x2, x3
i2: ADD x4, x1, x5   # needs i1
i3: SUB x6, x7, x8   # independent
i4: DIV x9, x4, x6   # needs i2 and i3

MUL takes 4 cycles, ADD and SUB 2, DIV 8. One instruction issues per cycle; one result per cycle on the bus.

instrissueexecutebroadcastwhy
i1 MUL12 – 56operands ready at once
i3 SUB34 – 57runs before i2; bus busy in cycle 6, so it broadcasts in 7
i2 ADD27 – 89woken by i1's broadcast in cycle 6
i4 DIV410 – 1718needs i2 (cycle 9) and i3 (cycle 7)

The table is sorted by when each instruction executes: i3 overtakes i2. One shared bus is a real limit — it delays i3 by a cycle.

Part 4 · Dynamic scheduling

Neither, though, could stop cleanly at an error: results were written the moment they were ready, in any order. That is the missing piece.

05

Putting results back in order

Execute in any order — but make the results official in program order.

Part 5 · Putting results back in order

The problem: errors in a scrambled world

  • Suppose an old instruction divides by zero — but a younger one has already overwritten a register. The program's state is now a mixture of "before" and "after".
  • An operating system or debugger needs a precise exception: every instruction before the faulting one has finished, none after it has changed anything, and the PC points exactly at the culprit.
Analogy

A kitchen cooks dishes in whatever order is quickest, but the waiter serves each table's courses strictly in order. If the soup is spoiled, nothing after it has reached the table yet.

Part 5 · Putting results back in order

The reorder buffer

The reorder buffer (ROB) is a queue holding every in-flight instruction in program order.

Instructions execute out of order and park their results in the ROB.

Only the instruction at the head may commit: make its result official and leave. Commit is strictly in order.

If the head faulted — or was a wrongly guessed branch — everything younger is thrown away. Clean, every time.

Part 5 · Putting results back in order

The modern out-of-order pipeline

Part 5 · Putting results back in order

Speculation: running ahead of branches

  • A branch comes every ~5 instructions. A big window would be useless if it stopped filling at each one.
  • So the core uses the branch predictor and keeps fetching, renaming and executing down the guessed path. This is speculation; such instructions may execute but cannot commit until the branch is confirmed.
  • Right guess: the work is already done — no penalty.
  • Wrong guess: every ROB entry younger than the branch is thrown away, the rename table is restored from a saved copy, and fetch restarts on the correct path. Only a few cycles lost.
Keep in mind

Wrong-path work leaves no trace in registers or memory. But it can leave traces elsewhere — the basis of the Spectre attacks in the security deck.

Part 5 · Putting results back in order

The hard case: loads and stores

  • A load may be ready while an older store's address is still unknown. Do they touch the same memory? Nobody knows yet.
  • The load/store queue (LSQ) keeps memory operations in program order.
  • If a load reads an address an older store is about to write, the queue hands over the store's data directly: store-to-load forwarding.
  • Aggressive cores let loads go early on a guess; if a store later turns out to overlap, the load and everything after it are redone.
06

Wider: several per cycle

Superscalar, VLIW and multithreading — three ways to fill a wide machine.

Part 6 · Wider: several per cycle

Superscalar: more than one per cycle

Everything so far starts at most one instruction per cycle: IPC ≤ 1. A superscalar core fetches, decodes, issues and commits several per cycle — 2, 4, 6 or more wide.

In-order superscalar

Fetches N per cycle but issues them in order; if one stalls, those behind it stall. Cheap and frugal. Arm Cortex-A53: two per cycle.

Out-of-order superscalar

Issues any ready instructions from a large window. Far higher IPC on real code, at a large area and power cost. Arm Cortex-A76: four per cycle.

Why not 16-wide?

To issue N instructions together, every pair must be checked against each other: about N² comparisons. Register-file ports and forwarding wires grow just as fast. Past 4–8 wide, the gains don't pay.

Part 6 · Wider: several per cycle

VLIW: let the compiler do it

Very long instruction word machines move scheduling into the compiler. Each long instruction bundles several operations the compiler has proved independent; the hardware just runs every slot together.

ForAgainst
Hardwaresimple, wide, low power—
Schedulingthe compiler can study the whole programcannot see run-time surprises such as a slow load
Code—tied to one machine width; empty slots waste space

VLIW thrives where code is regular — signal processing, AI accelerators (TI C6000 DSPs). It struggled on general code full of surprises (Intel Itanium). So CPUs went out of order and DSPs went VLIW.

Part 6 · Wider: several per cycle

SMT: fill the gaps with another thread

Even a wide out-of-order core rarely finds enough ready work in one thread to fill every slot every cycle.

Simultaneous multithreading (Intel calls it Hyper-Threading) keeps the registers and PC of two or more threads, and issues from all of them into the same execution units each cycle.

Cost: modest. Gain: typically 20–40% more throughput.

The catch: the two threads now share caches and units — a known route for leaks between them.

Part 6 · Wider: several per cycle

Check yourself

1. In add x1,x2,x3 then sub x2,x4,x5, what kind of dependence is there, and can renaming remove it?
2. If instructions execute out of order, why does the program never see a scrambled result?

Answer

1. WAR on x2 (add reads x2, sub later writes it): a false dependence. Renaming gives sub's x2 a new physical home, so yes.

2. They commit in program order from the reorder buffer. Only committed results are official, so the visible state always moves forward in order.

Part 6 · Wider: several per cycle

Recap

  • In order, one slow instruction freezes everyone behind it; out-of-order execution runs ready work from a window and hides the delay.
  • RAW is a true dependence. WAR and WAW are false — just reused names — and register renaming removes them.
  • Tomasulo: reservation stations, tags and a common data bus that wakes waiting instructions. The scoreboard came first but stalled on false dependences.
  • The reorder buffer commits in order: precise exceptions and clean recovery from wrong guesses. Speculation fills the window past branches; the load/store queue handles memory.
  • Superscalar issues several per cycle (checks grow as N²); VLIW hands scheduling to the compiler; SMT fills idle slots with a second thread.
