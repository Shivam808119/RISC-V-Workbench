RISC-V Cores

A comparison map for open RISC-V core designs, their goals and implementation trade-offs.

Core idea

RISC-V is an instruction-set architecture (ISA), not one particular processor. Many cores implement the ISA with different area, performance and feature trade-offs.

How to use this page

A core's actual MMU, cache, privilege, debug and extension support must be checked against its documentation and configuration. This page is an organized prototype/reference; the uploaded files remain the detailed source material for the concepts already covered there.

01

Why RISC-V is the perfect specimen

For the first time, the insides of real processors are open to read.

Part 1 · Why RISC-V is the perfect specimen

You can open the box

  • x86 and Arm cores are proprietary: you can measure them, never read their design.
  • RISC-V is an open standard, and there is a whole family of open-source cores whose full hardware descriptions anyone can download, simulate, change and even manufacture.
  • They all run the same instructions, yet differ by about 10 000× in size and speed. Compile one program, run it on any of them, and feel the microarchitecture.
Misconception

"RISC-V is a chip." It isn't — it is an instruction set, a specification. Saying "a RISC-V" is like saying "an x86" without naming a Ryzen or a Core i9.

02

Tiny cores: SERV and PicoRV32

When the goal is the smallest possible core, give up speed on purpose.

Part 2 · Tiny cores: SERV and PicoRV32

SERV: one bit at a time

SERV (by Olof Kindgren) is a complete RV32I core with a 1-bit-wide datapath. Its ALU is essentially a single full adder.

A 32-bit add takes 32 cycles, one bit per cycle, lowest bit first, with the carry saved between cycles. Such a design is bit-serial.

It fits in a few hundred FPGA cells — small enough for hundreds on one chip. It runs a real-time operating system.

Part 2 · Tiny cores: SERV and PicoRV32

PicoRV32: small and pragmatic

  • PicoRV32 (by Claire Wolf) has a full 32-bit datapath, but runs each instruction over several cycles, reusing the same hardware for each step.
  • It is a single, readable Verilog file; small, easy to drop into a design, and able to run at a high clock rate.
  • One of the most widely used open cores in hobby and industrial FPGA designs.
Part 2 · Tiny cores: SERV and PicoRV32

Single-cycle, multicycle, pipelined

StyleHowCostCPI
Single-cycleevery instruction in one long cyclethe clock must fit the slowest instruction1, but a slow clock
Multicycleeach instruction in several short steps, one after another, sharing one ALUsmall> 1
Pipelinedthe steps overlap across instructionspipeline registers + hazard logicclose to 1
In one line

Multicycle spends cycles to save area; pipelining spends area to save cycles. Bit-serial takes multicycle to the extreme by also shrinking the datapath to one bit.

03

In-order pipelines: Rocket and friends

The textbook five-stage pipeline, made real.

Part 3 · In-order pipelines: Rocket and friends

Rocket: the reference in-order core

  • Rocket, from UC Berkeley, is a 5-stage, in-order, single-issue pipeline: fetch, decode, execute, memory, write back.
  • Full forwarding, branch prediction, optional floating point, virtual memory with TLBs, and L1 caches. It boots Linux.
  • It is the Pipelining deck's diagram in real hardware: the same stages, the same forwarding paths, the same branch decided in EX.

In products

SiFive, founded by Rocket's authors, sells descendants: the E-series for microcontrollers and the S-series for 64-bit real-time work.

The Arm analogy

Rocket sits in the same niche as Arm's Cortex-A53 — the small, frugal, in-order "little" core inside countless phones.

04

Out of order: BOOM, CVA6, XiangShan

The full arsenal: wide issue, renaming, dynamic scheduling, speculation.

Part 4 · Out of order: BOOM, CVA6, XiangShan

BOOM: the Berkeley Out-of-Order Machine

BOOM stageWhat it doesThe idea behind it
Fetchfetches several instructions per cycle, with an advanced predictorbranch prediction, speculation
Decodedecodes several per cyclesuperscalar width
Renamemaps x0–x31 onto a larger physical register fileregister renaming
Issueinstructions wait in issue queues, fire when readyreservation stations
Executeseveral units in parallel: ALUs, memory, floating pointmultiple functional units
Commitretires in order from the reorder bufferprecise exceptions

Width, reorder-buffer size, register count and predictor size are all parameters: dial them, regenerate, measure.

Part 4 · Out of order: BOOM, CVA6, XiangShan

Two more points on the map

CVA6 (Ariane)

From ETH Zürich, now the OpenHW Group: a 6-stage, in-order, 64-bit application core in SystemVerilog that boots Linux. A scoreboard lets slow operations finish out of order — a pragmatic point between Rocket and BOOM. Built for industrial-grade verification.

XiangShan

From the Chinese Academy of Sciences: an aggressive, wide, deep out-of-order core aiming at desktop and server performance. Proof that "open" no longer means "slow".

05

Generators and the SoC

Not one design, but a program that writes a whole family of designs.

Part 5 · Generators and the SoC

Chisel: hardware as a generator

// Chisel: parameters in, hardware out
class MyConfig extends Config(
  new WithNBigCores(2) ++     // 2 Rocket cores
  new WithNBoomCores(1) ++    // + 1 BOOM core
  new DefaultConfig
)
// → Verilog → simulate, or build a chip

Chisel is a hardware construction language embedded in Scala. You write a generator: a program that, given parameters, produces synthesizable Verilog.

Change one number — cores, cache size, issue width — and regenerate.

Chipyard is Berkeley's framework that composes whole systems-on-chip from such generators: pick cores, caches, accelerators and peripherals, wire them over TileLink, then simulate, run on an FPGA, or take the design to manufacturing.

Part 5 · Generators and the SoC

The extension letters are a shopping list

LetterAddsHardware it implies

RV64GC = I, M, A, F, D plus C: the baseline for a Linux-class processor.

Part 5 · Generators and the SoC

From core to system-on-chip

Rich, coherent traffic rides the system bus; a register write to a UART rides a lightweight peripheral bus. Two fabrics on one chip, chosen by bandwidth and coherence needs.

Part 5 · Generators and the SoC

Check yourself

SERV and BOOM give bit-for-bit identical results on the same RV32I program, yet BOOM can be thousands of times faster. Where does the difference come from?

Answer

Entirely from the microarchitecture: a 32-bit datapath instead of 1 bit, pipelining instead of multicycle, several instructions per cycle, out-of-order issue, branch prediction and caches. The ISA says what; the microarchitecture decides how fast.

Part 5 · Generators and the SoC

Recap

  • Open RISC-V cores span the whole design space, which makes them the ideal specimens for studying microarchitecture.
  • SERV (bit-serial) and PicoRV32 (multicycle) trade cycles for tiny area.
  • Rocket is the classic 5-stage in-order pipeline; CVA6 a 6-stage industrial one.
  • BOOM and XiangShan are out-of-order superscalar cores whose stages map onto renaming, issue queues and the reorder buffer.
  • Chisel generators and Chipyard turn parameters into whole systems-on-chip, wired over TileLink, bridged to AXI and a peripheral bus.
