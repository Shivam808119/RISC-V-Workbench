01

The idea: an assembly line

Do not wait for one instruction to finish before starting the next.

Part 1 · The idea: an assembly line

Laundry, two ways

Each load still takes 3 hours. But as soon as load 1 moves to the dryer, load 2 can start washing. All three machines stay busy.

Part 1 · The idea: an assembly line

The same idea inside a processor

Pipelining splits the work of each instruction into stages, and lets a different instruction occupy each stage at the same time.

StageNameWhat happens
IFinstruction fetchread the instruction at the PC; work out PC + 4
IDdecodework out what it is; read its source registers
EXexecutethe ALU calculates, or compares for a branch
MEMmemoryloads read memory, stores write it
WBwrite backthe result goes into the destination register

Between stages sit pipeline registers: they capture each stage's results at the clock edge and hand them to the next stage, like trays passed down the line.

Part 1 · The idea: an assembly line

The staircase: a space-time diagram

instructionc1c2c3c4c5c6c7c8c9
lw x1,0(x2)IFIDEXMEMWB
add x3,x4,x5IFIDEXMEMWB
sub x6,x7,x8IFIDEXMEMWB
or x9,x10,x11IFIDEXMEMWB
and x12,x13,x14IFIDEXMEMWB

Rows are instructions, columns are clock cycles. By cycle 5 every stage is busy, and from then on one instruction finishes every cycle. Five instructions take 9 cycles instead of 25.

Part 1 · The idea: an assembly line

Two numbers people mix up

Latency

How long one instruction takes from start to finish. Pipelining does not shorten it — each still passes through all five stages, and the pipeline registers even add a little delay.

Throughput

How many instructions finish per second. This is what pipelining improves: one per cycle instead of one per five.

There is a second win: each stage does about a fifth of the work, so the clock period can be about five times shorter.

Misconception

"Pipelining makes each instruction faster." It doesn't. A car still spends the same time on the assembly line — the factory just finishes more cars per hour.

Part 1 · The idea: an assembly line

How much faster, ideally?

With N stages and k instructions:

  • without pipelining: N × k cycles
  • with pipelining: N + (k − 1) cycles — N to fill the line, then one per cycle

As k grows, the speed-up approaches N.

k5 × k5 + k − 1speed-up
52592.8×
1005001044.8×
10 00050 00010 0045.0×

Real pipelines never quite reach N: stages are never perfectly equal, the pipeline registers cost time, and — above all — instructions get in each other's way.

02

Hazards: when the line jams

The staircase assumed every instruction is independent. Real programs are not.

Part 2 · Hazards: when the line jams

Three families of hazard

A hazard is anything that stops the next instruction from going ahead in its planned cycle.

Structural

Two instructions need the same piece of hardware in the same cycle.

Data

An instruction needs a result that an earlier one has not produced yet.

Control

The processor does not yet know which instruction comes next, because a branch is undecided.

Analogy

On the laundry line: one machine that both washes and dries (structural); you can't fold what hasn't dried (data); you don't know if the next load is whites or colours until you've checked the basket (control).

Part 2 · Hazards: when the line jams

Structural hazards: one tool, two hands

Suppose instructions and data share one memory port. In cycle 4 of the staircase, lw is in MEM reading data while or is in IF fetching itself. Both want the port.

The textbook fix: give the pipeline separate memories for instructions and data, and a register file that can be read and written in the same cycle.

When duplicating is too costly — a single big divider, say — the later instruction simply has to wait.

Part 2 · Hazards: when the line jams

Data hazards: the result isn't ready

add x1, x2, x3   # writes x1 in WB, cycle 5
sub x4, x1, x5   # reads x1 in ID, cycle 3 — too early!
and x6, x1, x7   # reads x1 in ID, cycle 4 — still too early

Three patterns are possible when two instructions touch the same register:

NamePatternA problem in this in-order pipeline?
RAWread after write — a later instruction needs an earlier one's resultyes: a true dependence — data really flows
WARwrite after read — a later write must not overtake an earlier readno: everything happens in order
WAWwrite after write — two writes must land in orderno: same reason

WAR and WAW matter once instructions can run out of order — the next deck.

Part 2 · Hazards: when the line jams

Control hazards: which way next?

    beq x1, x2, TARGET   # equal? not known until EX
    add x3, x4, x5       # already being fetched — wrong if the branch is taken
    ...
TARGET:
    sub x6, x7, x8
  • By the time the branch is decided in EX, IF has already fetched the next instructions in line.
  • If the branch is taken, those instructions are wrong and must be thrown away.
  • Branches are 15–25% of all instructions, so this is the biggest single threat to a pipeline's speed.
03

Fixing data hazards

Wait if you must — but mostly, take a short cut.

Part 3 · Fixing data hazards

The simple fix: wait

A stall holds an instruction in its stage for a cycle, while an empty slot — a bubble — travels down the pipeline in its place.

Without forwarding

The dependent instruction waits until the producer writes its result to the register file. These stalls reduce throughput.

Without help, sub waits two cycles: it can only read x1 in the same cycle that add writes it back. (The register file writes in the first half of a cycle and reads in the second.)

Part 3 · Fixing data hazards

The clever fix: forwarding

The add's answer exists at the end of its EX stage (cycle 3). It is only written in cycle 5.

Forwarding (also called bypassing) adds wires that carry a fresh result straight from a pipeline register into the ALU input of the next instruction — skipping the register file.

  • EX/MEM → EX: from the instruction one ahead.
  • MEM/WB → EX: from the instruction two ahead.

With both paths, every ALU-to-ALU dependence costs zero stalls. Turn forwarding on below:

Part 3 · Fixing data hazards

Try it: forwarding on and off

With forwarding

ALU results can be routed from EX/MEM or MEM/WB directly to a later instruction’s EX inputs. This removes most ALU-to-ALU stalls, but not the immediate load-use stall.

Part 3 · Fixing data hazards

The one case forwarding can't fully fix

lw  x1, 0(x2)    # the value arrives at the END of MEM (cycle 4)
add x3, x1, x4   # needs it at the START of EX (cycle 4)
  • A load's value only exists after the memory stage. The very next instruction wants it in the same cycle.
  • No wire can carry a value backwards in time. So a load followed immediately by its use — a load-use hazard — costs exactly one stall, after which forwarding delivers the value.
The compiler's trick

Move an unrelated instruction between the load and its use. The bubble is filled with useful work. Pick "Load then use", then "Load, reordered", on the next slide.

Part 3 · Fixing data hazards

Try it: hide the load-use bubble

Load-use timing

A load produces its value only at the end of MEM. If the next instruction needs it immediately, insert one bubble; forwarding can then deliver the loaded value to EX.

lw: IFIDEXMEM → value readyWB
04

Fixing control hazards

Don't wait for the branch — guess, and be right almost every time.

Part 4 · Fixing control hazards

Three simple options

StrategyHow it worksCost
Stallfetch nothing until the branch is decidedpay the full delay on every branch
Assume not takenkeep fetching the next instructions in line; if the branch is taken, flush them — throw them awayfree when not taken; a penalty when taken
Delayed branchthe ISA says the instruction after a branch always runs; the compiler fills that slotbakes one pipeline's depth into the ISA forever

MIPS and early SPARC used delayed branches. It aged badly as pipelines grew deeper, and RISC-V deliberately has none.

Part 4 · Fixing control hazards

The real answer: predict

Branch prediction guesses each branch's direction (and target) at fetch time, keeps fetching down the guessed path, and only pays a penalty when the guess was wrong.

PredictorHow it guessesTypical accuracy
Statica fixed rule, e.g. "backward branches are taken" (loops jump back)65–80%
1-bit"whatever this branch did last time"misses twice per loop
2-bit counterneeds two surprises in a row to change its mind85–93%
Correlating (gshare)also looks at what the last few branches did95% and more

Modern predictors are right 95–99% of the time, so most branches cost nothing at all.

Part 4 · Fixing control hazards

The 2-bit saturating counter

This is a saturating counter. The top bit is the guess. One odd result only nudges it from "strongly" to "weakly" — the guess does not flip.

Analogy

A friend who is late once is still "usually on time". It takes two late arrivals in a row before you change your expectation.

Part 4 · Fixing control hazards

Try it: 1-bit against 2-bit

Predictor comparison

Compare static prediction, a 1-bit last-outcome predictor, and a 2-bit saturating counter. The 2-bit counter tolerates one unusual outcome without immediately reversing its prediction.

Part 4 · Fixing control hazards

Why 2 bits beat 1 bit on loops

A loop runs 100 times: its closing branch is taken 99 times, then not taken once to exit. The loop is entered again later.

1-bit: 2 misses per loop

Wrong at the exit (it expected taken). Then it remembers "not taken" — and is wrong again on the first pass next time.

2-bit: 1 miss per loop

Sits at strongly taken. The exit only nudges it to weakly taken — still guessing taken — so the next entry is right.

On programs full of loops, halving the misses is a large win. In the widget's short loop of 4, the 2-bit counter is right 69% of the time, the 1-bit only 50%.

Part 4 · Fixing control hazards

Predicting where, not just whether

  • Knowing a branch is taken is not enough: the fetch stage also needs the target address, and it needs it now.
  • A branch target buffer (BTB) is a small table, looked up with the branch's own address, that remembers where it jumped last time.
  • Together, direction predictor + BTB let fetch redirect itself in the very cycle it meets a branch.
05

Deeper pipelines, and the arithmetic of stalls

More stages give a faster clock — and a bigger bill for every mistake.

Part 5 · Deeper pipelines, and the arithmetic of stalls

Why not 20 stages?

Superpipelining splits the work into many more, shorter stages — 10, 15, even 31 — so the clock can tick faster.

Gains

A shorter clock period. More instructions in flight. Great for long, predictable streams of work.

Costs

A wrong branch guess now flushes ~15 instructions, not 2. Results travel further to be forwarded. Pipeline-register overhead eats into each shorter stage. Power rises.

The Pentium 4 pushed to 20–31 stages chasing gigahertz — and lost to designs with fewer stages and better CPI. Deep pipelines demand excellent prediction.

Part 5 · Deeper pipelines, and the arithmetic of stalls

Worked example: effective CPI

A five-stage pipeline with forwarding. Ideal CPI = 1. Add the average stall cycles per instruction:

  • Loads are 25% of instructions; half are followed straight away by their use → 1 stall each.
  • Branches are 20%; 10% of them are mispredicted → 3 stall cycles each.
load-use stalls   = 0.25 × 0.50 × 1 = 0.125
branch mispredict = 0.20 × 0.10 × 3 = 0.060
---------------------------------------------
effective CPI     = 1 + 0.125 + 0.060 = 1.185

About 16% slower than ideal. A better predictor (3% wrong) cuts the branch term to 0.018: CPI ≈ 1.14.

Formula

effective CPI = 1 + Σ (how often × how many cycles lost)

Part 5 · Deeper pipelines, and the arithmetic of stalls

Check yourself

1. A 5-stage pipeline runs 1 000 independent instructions. How many cycles?
2. With forwarding, how many stalls does lw x5,0(x1) followed by add x6,x5,x5 cost?
3. Why might a real 5-stage pipeline only be 3–4× faster, not 5×?

Answer

1. 5 + 999 = 1 004 cycles.

2. One — a load-use hazard.

3. Load-use bubbles, branch mispredictions, shared units, the time to fill and drain, and stages of unequal length (the slowest sets the clock).

Part 5 · Deeper pipelines, and the arithmetic of stalls

Recap

  • Pipelining overlaps the stages IF · ID · EX · MEM · WB. It raises throughput and the clock rate, not the latency of one instruction.
  • Hazards: structural (shared hardware), data (RAW is the real one in order), control (branches).
  • Forwarding removes almost all data stalls; a load followed by its use still costs one bubble, which compilers fill.
  • Branch prediction answers control hazards: a 2-bit counter misses once per loop where 1 bit misses twice; a BTB supplies the target.
  • Deeper pipelines clock faster but pay more per mistake. Effective CPI = 1 + Σ (frequency × penalty).
