The core, explained

VexRiscv is written in SpinalHDL and built from plugins. Each feature, such as the multiplier, MMU, caches or debug port, is a plugin you switch on or off.

Because every feature is a plugin, its security depends on what you switch on. A custom-function-unit plugin can also attach your own crypto instructions.

That is why one name covers anything from a tiny FPGA core to a Linux-capable one. It also means two VexRiscv chips can have very different security, so the plugin list is the real specification.

2

Memory it uses, and why

Memory is where speed and security meet. Here is every memory part in VexRiscv, with the reason it is there.

Register fileFrom a RegFilePlugin, usually block RAM.
Why it is here: The register file is a plugin so an FPGA can use block RAM or flip-flops, whichever is cheaper.
Instruction pathSimple uncached bus, or a cached bus plugin.
Why it is here: The simple bus gives minimal logic. The cached bus adds speed for slow external memory.
Data pathSimple bus or write-through cache. IO ranges bypass the cache.
Why it is here: Write-through keeps memory current, and IO ranges stay uncached so devices behave.
MMU and PMPMmuPlugin for Sv32 pages and PmpPlugin for regions, both optional.
Why it is here: The MMU is only added for Linux. PMP gives lighter protection for microcontroller uses.
Multi-coreVexRiscvSmpCluster adds coherence for Linux builds.
Why it is here: The SMP cluster is an option for multi-core Linux builds that need shared memory.
Follow one load. In the simple build, the DBusSimplePlugin sends the address to the bus. With DBusCachedPlugin, the write-through cache answers hits and sends misses out. IO ranges always bypass the cache so device registers stay correct. If MmuPlugin is on, the TLB translates first.
3

Security it uses, and why

Every plugin you add changes the attack surface, so the secure VexRiscv is the one you configure carefully: barrel shifter, no leftover debug port, MMU or PMP on, and extra hardening where needed.

StoppedPartlyExposed by the core on its own
StoppedSpectre, MeltdownThe attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What VexRiscv does: In order, and permission faults hit before younger instructions act.
PartlyPrivilegeThe attack: A bug or hostile program tries to touch memory that is not its own, or to run data as code. Hardware has to say no, because software cannot be trusted to.
What VexRiscv does: CsrPlugin, MMU and PMP give full isolation if you enable them.
PartlyTiming leaksThe attack: If an instruction takes longer for certain values, anyone who can time it can work backwards to the secret. Early-exit divide and variable shifts are common causes.
What VexRiscv does: LightShifter leaks shift amounts. Pick the full barrel shifter and fixed multiplier.
PartlyCache timingThe attack: The attacker times memory accesses to learn what another program touched. A fast access means the line was cached. It needs a cache that two programs share.
What VexRiscv does: Optional caches can be probed across context switches.
ExposedDebug backdoorThe attack: A debug port left switched on can read and write registers and memory, so anyone who reaches it owns the chip.
What VexRiscv does: A DebugPlugin left in a product gives an attacker full access.
ExposedPower, glitchesThe attack: Physical attacks: reading a secret from the power trace, or glitching voltage, clock or laser so the chip skips a check. Radiation can also flip bits by accident.
What VexRiscv does: No default ECC or lockstep. Add your own via plugins.

You get exactly the security you configure, no more.
