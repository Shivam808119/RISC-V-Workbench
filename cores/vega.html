VEGA

India’s home-grown DIR-V family. It runs from a 3-stage microcontroller (ET1031) up to a 16-stage out-of-order quad core (AS4161).

The core, explained

VEGA is a family, not one core. C-DAC in India designed it under the DIR-V programme, so the country has processors whose design it can fully inspect.

One family covers the whole range. Small cores run RTOS code, while the 64-bit cores run Linux with an MMU. VEGA powers the THEJAS32 and THEJAS64 chips.

At the small end are 32-bit microcontroller cores. At the top are 64-bit out-of-order cores with caches and an MMU that run Linux. Which memory and security story applies depends on which VEGA you pick.

2

Memory it uses, and why

Memory is where speed and security meet. Here is every memory part in VEGA, with the reason it is there.

Register filesEach model has its own, plus buffers for the out-of-order models.
Why it is here: The wider out-of-order models need more registers and buffers to keep many instructions in flight.
L1 caches8 KB each on AS1061, 32 KB each from AS1161 up. ET1031 runs from plain SRAM.
Why it is here: Caches hide the slowness of main memory in the application cores. The microcontroller skips them to stay predictable.
Shared L2512 KB on the dual-core AS2161, 1 MB on the quad-core AS4161.
Why it is here: One shared L2 lets cores exchange data fast instead of going out to main memory.
MMU and TLBsVirtual memory on the application cores, with optional Sv32 or Sv39.
Why it is here: Linux needs virtual memory so each program sees its own address space.
CoherenceACE keeps cores in agreement. Memory ordering follows RVWMO.
Why it is here: ACE coherence stops cores from reading stale copies of shared data.
Follow one load on AS2161. The core checks the TLB, then the 32 KB L1 data cache. A miss goes over ACE to the shared 512 KB L2, and the coherence protocol makes sure the other core sees the same value. The small ET1031 skips all this and reads uncached SRAM.
3

Security it uses, and why

Threats depend on the model. Small in-order cores face almost none of the microarchitectural attacks. The 16-stage out-of-order models need the same scrutiny as any speculative design, and shared L2 on the multi-core models is a place for cross-core timing attacks.

StoppedPartlyExposed by the core on its own
StoppedProcess isolationThe attack: A bug or hostile program tries to touch memory that is not its own, or to run data as code. Hardware has to say no, because software cannot be trusted to.
What VEGA does: M/S/U modes, the MMU and PMP keep programs apart on the application cores.
PartlySpectre, MeltdownThe attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What VEGA does: In-order models do not speculate loads. The out-of-order models are not described in public docs, so check before trusting them.
PartlyCache timingThe attack: The attacker times memory accesses to learn what another program touched. A fast access means the line was cached. It needs a cache that two programs share.
What VEGA does: Uncached SRAM on ET1031 is clean. Shared L2 caches on AS2161 and AS4161 can leak.
ExposedTiming leaksThe attack: If an instruction takes longer for certain values, anyone who can time it can work backwards to the secret. Early-exit divide and variable shifts are common causes.
What VEGA does: No hardware constant-time claim, so write constant-time code.
PartlySupply chainThe attack: Hidden malicious logic added during design or manufacture, which no test of the finished chip is sure to find.
What VEGA does: Auditable home-grown RTL reduces the risk of hidden hardware. Fault and power defences sit in the SoC.

Strong on trust and isolation, and the out-of-order cores need their speculation story proven.
