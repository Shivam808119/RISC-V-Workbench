The core, explained

SonicBOOM, also called BOOMv3, is the mature version: up to four instructions per cycle, a TAGE-L predictor and a banked data cache that handles many misses at once.

A 128-entry reorder buffer and branch masks let it recover quickly from wrong guesses. That speed also means wrong-path loads can leave traces in the caches.

It is the open-source core that gets closest to commercial performance, which also makes it the best open example for studying speculative-execution attacks.

2

Memory it uses, and why

Memory is where speed and security meet. Here is every memory part in SonicBOOM, with the reason it is there.

Register files and maps128 physical integer and FP registers with rename maps.
Why it is here: More physical registers let many instructions be in flight at once.
Load and store queuesLDQ and STQ with speculative memory disambiguation.
Why it is here: Queues let loads run before older stores are known, which gains speed and costs safety.
L1 cachesInstruction cache, and a banked 32 KB data cache with 8 MSHRs.
Why it is here: Banking and 8 MSHRs let the cache serve several accesses and track many misses together.
TranslationL1 ITLB, dual-ported DTLB, shared L2 TLB and page walker.
Why it is here: A second-level TLB cuts costly page walks, which matter in a wide out-of-order core.
L2Shared, inclusive, with TileLink MESI coherence.
Why it is here: The shared L2 and coherence keep many cores consistent.
Follow one load. The load queue issues it early to the banked L1 data cache, where one of 8 MSHRs tracks a miss. A branch mask tags the load so it can be killed in one cycle if the branch was wrong. The data, and the cache line, may already have changed state.

Security it uses, and why

More width and a stronger TAGE predictor mean more speculation to learn from. Meltdown is handled in the first memory stage, but Spectre v1, v2 and v4 and cache timing are present in baseline RTL, so research builds add partitioning and fences.

StoppedPartlyExposed by the core on its own
ExposedSpectre v1The attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What SonicBOOM does: Wrong-path loads leave secret-indexed lines in the L1 data cache.
ExposedSpectre v2The attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What SonicBOOM does: Shared µBTB, BTB, TAGE tables and return stack can be mistrained.
ExposedSpectre v4The attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What SonicBOOM does: Younger loads can read stale data before older store addresses resolve.
StoppedMeltdownThe attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What SonicBOOM does: DTLB and PMP checks in the first memory stage stop faulting data.
ExposedCache timingThe attack: The attacker times memory accesses to learn what another program touched. A fast access means the line was cached. It needs a cache that two programs share.
What SonicBOOM does: Shared L1 and L2 leak unless partitioned (DAWG-style research).
StoppedIsolationThe attack: A bug or hostile program tries to touch memory that is not its own, or to run data as code. Hardware has to say no, because software cannot be trusted to.
What SonicBOOM does: M/S/U, Sv39 and PMP work with Keystone.

The fastest core here and the one with the most to defend.
