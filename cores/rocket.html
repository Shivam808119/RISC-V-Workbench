The core, explained

Rocket is Berkeley’s in-order 64-bit core and the reference design for the Chipyard and Rocket Chip generators. It has the five classic stages and is complete enough to boot Linux.

This is the textbook pipeline in real hardware: fetch, decode, execute, memory, write back. SiFive’s cores descend from it.

Its parts are well understood, so many other designs borrow from it, including BOOM. If you want to learn how a real pipeline, cache and MMU fit together, Rocket is the model.

2

Memory it uses, and why

Memory is where speed and security meet. Here is every memory part in Rocket, with the reason it is there.

Register files and scoreboardTracks slow loads and divides while the pipeline keeps moving.
Why it is here: The scoreboard lets the in-order pipeline keep going while a slow load or divide finishes.
L1 instruction cacheVirtually indexed. Can be swapped for an ITIM scratchpad.
Why it is here: The instruction cache keeps loops close. ITIM gives a cache-free option with fixed timing.
L1 data cache (HellaCache)Non-blocking, or a DTIM scratchpad instead.
Why it is here: The non-blocking data cache keeps working during a miss. DTIM again gives fixed timing.
TLBs, page walker, PMPSv39/Sv48 translation, with PMP checked on every physical address.
Why it is here: Sv39 gives each program its own address space and PMP lets machine mode lock regions.
Shared L2TileLink with MESI coherence and RVWMO ordering.
Why it is here: A shared L2 and MESI coherence keep many Rocket tiles consistent.
Follow one load. The DTLB translates the address and PMP checks it in the same stage. A hit in the non-blocking L1 returns the data. A miss goes over TileLink to the shared L2 while the scoreboard lets later instructions continue. A fault cancels the load before data is written.
3

Security it uses, and why

Rocket is the reference for safe-by-ordering: branches resolve before memory is touched, so Spectre v1 and Meltdown on the data cache fail. What remains is classic cache timing across programs, which Keystone and ITIM/DTIM scratchpads address, plus bit flips that ECC covers.

StoppedPartlyExposed by the core on its own
StoppedMeltdownThe attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What Rocket does: A faulting load is cancelled in the memory stage, before its data can be used.
StoppedSpectre v1The attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What Rocket does: Branches resolve in execute, before the data cache is touched in memory.
PartlyCache timingThe attack: The attacker times memory accesses to learn what another program touched. A fast access means the line was cached. It needs a cache that two programs share.
What Rocket does: Shared L1 and L2 can be probed. Scratchpads or partitioning remove the cache.
StoppedOS and enclave isolationThe attack: A bug or hostile program tries to touch memory that is not its own, or to run data as code. Hardware has to say no, because software cannot be trusted to.
What Rocket does: Modes, page tables and PMP are the base of Keystone enclaves.
PartlyBit flipsThe attack: Physical attacks: reading a secret from the power trace, or glitching voltage, clock or laser so the chip skips a check. Radiation can also flip bits by accident.
What Rocket does: Optional SECDED ECC or parity on L1 and L2 memory.

A good base for isolation, with its caches the weak point.
