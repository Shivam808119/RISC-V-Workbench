The core, explained

Ibex started as ETH Zürich’s Zero-riscy and is now maintained by lowRISC. It is the main CPU of OpenTitan, an open-source chip whose job is to be the root of trust for a computer.

Where most cores chase speed, Ibex is built to resist attack. Its SecureIbex mode adds a shadow core, error-correcting memory, fixed-time maths, and decoy instructions.

It is a short in-order pipeline, so there is little to attack in the first place. On top of that, the SecureIbex options add the defences a lab attacker would need to beat: a second core in lockstep, ECC everywhere, fixed timing and decoy activity.

Memory it uses, and why

Memory is where speed and security meet. Here is every memory part in Ibex, with the reason it is there.

Register file32 registers, protected by a 39-bit ECC code.
Why it is here: ECC on the registers catches a flipped bit that could change a security decision.
Prefetch buffer and I-cacheA tiny queue, plus an optional 2-way cache whose contents are scrambled with the PRINCE cipher and ECC.
Why it is here: A tiny prefetch queue keeps the pipeline fed. Scrambling the cache makes it hard to aim at specific lines.
Load-store unitNo data cache at all. Data goes straight to on-chip SRAM, so timing is predictable.
Why it is here: With no data cache, load time never depends on earlier loads, so there is no data-cache timing channel.
BusOBI or TileLink ports carry integrity bits from end to end.
Why it is here: Integrity bits on the bus catch tampering between the core and memory.
PMPUp to 16 regions with Smepmp locking down machine mode. No MMU.
Why it is here: PMP lets firmware set rules for memory. Smepmp stops machine mode from being tricked into breaking them.
Follow one fetch. The prefetch buffer asks the I-cache. On a miss the line comes in over OBI with its integrity bits checked, and the cache stores it scrambled with a PRINCE key, protected by ECC. A data load skips caches entirely and reads scratchpad SRAM in a fixed time.

Security it uses, and why

Ibex assumes a physical attacker: someone probing power, glitching the clock, or firing a laser. So it defends in layers. Fixed timing hides data from software, decoy instructions blur the power trace, ECC and the shadow core notice injected faults, and Smepmp keeps firmware from rewriting its own rules.

StoppedPartlyExposed by the core on its own
StoppedTiming leaksThe attack: If an instruction takes longer for certain values, anyone who can time it can work backwards to the secret. Early-exit divide and variable shifts are common causes.
What Ibex does: Data-independent timing makes divide, multiply and branches take a fixed time.
StoppedCache timingThe attack: The attacker times memory accesses to learn what another program touched. A fast access means the line was cached. It needs a cache that two programs share.
What Ibex does: No data cache, and the instruction cache is scrambled.
StoppedSpectre, MeltdownThe attack: Spectre makes a core guess a wrong path and leave traces in the cache. Meltdown reads protected data before the permission check lands. Both need a core that runs ahead of itself.
What Ibex does: In order, with no dynamic predictor to mistrain.
PartlyPower analysisThe attack: Physical attacks: reading a secret from the power trace, or glitching voltage, clock or laser so the chip skips a check. Radiation can also flip bits by accident.
What Ibex does: A random generator inserts dummy instructions to hide the real power pattern.
StoppedFault injectionThe attack: A bug or hostile program tries to touch memory that is not its own, or to run data as code. Hardware has to say no, because software cannot be trusted to.
What Ibex does: A delayed lockstep shadow core, ECC and shadow CSRs catch glitches.

What Ibex does: M/U modes and Smepmp stop code from writing its own ROM or running user pages.

Security is the design goal here, not an add-on.
